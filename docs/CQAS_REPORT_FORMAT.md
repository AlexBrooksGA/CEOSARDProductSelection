# C-QAS report format (`cqas-report/2`)

A C-QAS report records the checks C-QAS ran for **one product**:

- PFS findings for the requirements C-QAS checks automatically
- a geometric test and, where one is defined for the product type, a radiometric test, on **one input scene** over a cal/val site
- optionally, a **series**: the same test repeated over many scenes at cal/val sites, in the style of the CEOS Product Validation Platform (CEOS-PVP)

One JSON file per product drives the C-QAS section of the Product Explorer, the C-QAS row in the comparison and the copied selection summary.

> **Current status.** The C-QAS system that runs the metadata, geometric and radiometric tests is still being built. Every report is an **example** (`data_status: "example"`), generated by `tools/build_cqas_examples.mjs` to be plausible for its product (see [Example reports](#example-reports)). Every view shows these reports as "Example data". When C-QAS produces real output, it writes this format and the example file is replaced; no view code needs to change.

## What a report is, and is not

| Layer | Source | Meaning |
|---|---|---|
| CEOS MIM database | Agency survey | What the mission and instrument are, as declared |
| CEOS-ARD assessment | Self-assessment and WGCV peer review against a PFS | The product collection conforms at Threshold or Goal |
| **C-QAS report** | C-QAS runs on scenes over cal/val sites | What was measured for those scenes |

A C-QAS report is **not** a CEOS-ARD assessment, does not establish collection-wide suitability, and never affects filtering, matching or ordering in the Product Explorer.

## Changes from `cqas-report/1`

| v1 | v2 |
|---|---|
| — | `domain`: `optical`, `thermal` or `radar` |
| — | `findings_scope`: which requirements were checked and why |
| `geometric` | adds `kind` (`relative` or `absolute`) and `match_unit` |
| `radiometric` (always present) | may be `null`, with `radiometric_note` saying why |
| `radiometric.bands`, `headline_band`, `headline_band_name` | `channels` (each with an optional `name` and `reference_value`) and `headline_channel` |
| `radiometric.units` | adds `quantity`, `short_quantity`, `decimals`, `limit`, `limit_source` |
| `radiometric.pixels_used`, `pixels_total` | `samples_used`, `samples_total`, `sample_unit` |
| — | `series` (optional) |

A v1 file is rejected with a message naming the expected schema. The C-QAS reporting demo (`CEOSARD-CQAS-Reporting`) still reads v1, so it needs updating before its embedded copy is refreshed from this repository.

## Location and naming

`data/cqas/<product-id>.json`, where `<product-id>` is the curated product's stable ID (for example `landsat-c2-sr`).

**Validation.** `npm test` fails if any report is invalid, has an unknown field, refers to a product that is not in the curated catalogue, is not named after its product, or duplicates another report. It also fails if a curated product has no report, or if the files differ from what the generator writes. When the server starts, the same problems only skip that report with a logged warning, so a bad C-QAS file can never stop discovery, filtering or comparison.

**What each page receives.** Every page gets a short summary of each report (three lines and the provenance), used by the comparison and the copied summary. The full report is sent only with its own product page.

## Fields

Required unless marked *optional* (optional fields may be `null` or omitted). Fields not listed here are rejected. Dates are real ISO calendar dates, `YYYY-MM-DD`.

### Top level

| Field | Type | Meaning |
|---|---|---|
| `schema` | `"cqas-report/2"` | Format version. A breaking change uses a new version. |
| `data_status` | `example` \| `provisional` \| `reviewed` | `example`: mock values. `provisional`: produced by C-QAS, not reviewed. `reviewed`: reviewed output. Views label anything other than `reviewed` in one banner. |
| `status_note` | text | One sentence shown in the banner. |
| `report_id` | text | Report identifier, e.g. `DEMO-L8-001`. |
| `report_date` | date | Date the report was produced. |
| `domain` | `optical` \| `thermal` \| `radar` | Measurement domain. |
| `findings_scope` | text | Which requirements were checked and why; shown under the findings headline ("Results for …"). |
| `findings_summary` | text | One plain sentence summarising the Not met findings. |
| `radiometric_note` | text, *optional* | Required when `radiometric` is `null`: why no radiometric test is defined. |
| `next_action` | text | The single most important action for the data provider (Simple view). |
| `next_actions` | list of text | All actions for the data provider (Advanced view). |
| `scope_note` | text | The scope statement shown at the foot of every view. |

### `product`

| Field | Type | Meaning |
|---|---|---|
| `explorer_id` | stable ID | Product Explorer product ID. Must exist in the curated catalogue, and the file must be named `<explorer_id>.json`. |
| `name` | text | Product name as checked (may be narrower than the catalogue record, e.g. one mission). |
| `short_name` | text | Short label for headings. |

### `pfs`

| Field | Type | Meaning |
|---|---|---|
| `name`, `short_name` | text | PFS family, e.g. `Surface Reflectance`, `SR`. |
| `version` | text | PFS version the checks used, e.g. `5.0.2`. Views warn when this differs from the version of the product's CEOS-ARD assessment. |
| `total_requirements` | integer ≥ 1 | Requirements in the PFS. Counts are always shown against it ("9 of 36"). |

### `scene`

| Field | Type | Meaning |
|---|---|---|
| `product_id` | text | Provider scene, tile or frame identifier. |
| `platform`, `instrument` | text | E.g. `Landsat 8`, `OLI`. |
| `acquisition_date` | date | For a mosaic, its reference date. |
| `path`, `row` | integer, *optional* | WRS path and row, where applicable. |
| `reference_site` | object, *optional* | `network`, `code`, `name`, e.g. RadCalNet `RVUS` Railroad Valley Playa. |
| `note` | text, *optional* | Caveat about the input scene. |

### `run`

| Field | Type | Meaning |
|---|---|---|
| `code` | text | Run code. Must equal the segment codes joined by `-`. Shown under "Provenance" at the foot of the Advanced view. |
| `segments` | list | Each `{ code, part, meaning }`; explains one part of the run code. |
| `snapshot` | text | Assessment snapshot identifier. |
| `reviewer` | text, *optional* | `null` shows "Reviewer unassigned". |
| `note` | text, *optional* | |

### `findings` (list, at least one)

| Field | Type | Meaning |
|---|---|---|
| `requirement` | text | PFS requirement name. |
| `id` | text | PFS requirement identifier (category prefix + requirement ID), unique within the report. |
| `threshold`, `goal` | `Met` \| `Not met` \| `Not assessed` \| `Not required` | Outcome at each PFS level. `Not assessed` means not tested; `Not required` means the PFS has no requirement at that level. |
| `reason` | text, *optional* | Why a requirement is Not met or Not assessed. |

### `geometric`

| Field | Type | Meaning |
|---|---|---|
| `label`, `method`, `reference`, `comparison` | text | Test identity, method version, reference and comparison type. |
| `kind` | `relative` \| `absolute` | `relative`: image to image (e.g. repeat pass). `absolute`: against surveyed ground positions (e.g. corner reflectors). Views call the value "relative geometric error" or "location error". |
| `method_notes` | text, *optional* | |
| `pixel_size_m` | number > 0 | Native grid, used to convert pixels to metres. |
| `radial_rmse_px` | number | Headline radial RMSE in pixels, as reported by C-QAS over all accepted matches. |
| `comparisons_px` | list of numbers | Radial error of each comparison or reflector, in pixels (plotted as unordered dots). |
| `limit_px`, `limit_source` | number, text, *optional* | Numeric limit and where it comes from. `limit_source` is required when `limit_px` is given. |
| `matches_accepted`, `matches_total` | integers | Accepted ≤ total. |
| `match_unit` | text | What a match is, e.g. `image matches`, `corner reflectors`. |
| `positional_uncertainty` | text, *optional* | `null` shows "not estimated". |
| `absolute_accuracy`, `numeric_test`, `requirement_result` | `Met` \| `Not met` \| `Not assessed` | Absolute accuracy against an independent reference; the numeric limit test; the full PFS requirement. Views show the measured value and the requirement as two separate lines. |
| `requirement_reason` | text, *optional* | Why the full requirement is not met. |

### `radiometric` (object or `null`)

| Field | Type | Meaning |
|---|---|---|
| `label`, `method`, `reference`, `comparison` | text | As for geometric. |
| `method_notes` | text, *optional* | |
| `quantity`, `short_quantity` | text | E.g. `surface reflectance` / `SR`, `surface temperature` / `ST`, `radar cross-section` / `RCS`. |
| `units` | text | `1` (unitless), `K` or `dB`. |
| `decimals` | integer 0–4 | Decimal places to show. |
| `headline_channel` | text | Channel shown in the headline; must be one of `channels`. |
| `channels` | list | Each `{ channel, name, difference, uncertainty_k1, reference_value }` with unique channel codes: observed minus reference, standard uncertainty at k = 1, an optional plain `name` (e.g. `red`) and an optional `reference_value`. When given, views also show the difference as a percentage of it. Views derive k = 2 by doubling. |
| `limit`, `limit_source` | number, text, *optional* | Agreed limit on the absolute difference. `limit_source` is required when `limit` is given. |
| `samples_used`, `samples_total` | integers | Used ≤ total. |
| `sample_unit` | text | What a sample is, e.g. `pixels in the site window`, `corner reflectors`. |
| `unique_exclusions` | integer, *optional* | |
| `product_uncertainty` | text, *optional* | `null` shows "missing". |
| `accuracy_test`, `uncertainty_goal` | `Met` \| `Not met` \| `Not assessed` | |
| `accuracy_reason`, `uncertainty_goal_reason` | text, *optional* | |

### `series` (object, *optional*)

| Field | Type | Meaning |
|---|---|---|
| `test` | `radiometric` \| `geometric` | Which test is repeated. A radiometric series needs a `radiometric` test. |
| `description` | text | What is plotted, e.g. `Red (B4) surface reflectance difference`. |
| `channel` | text, *optional* | For a radiometric series, one of `radiometric.channels`; `null` for a geometric series. |
| `units`, `decimals` | text, integer 0–4 | As for radiometric (a geometric series uses `m`). |
| `sites` | list | Each `{ network, code, name }`, unique codes. Each site gets its own marker shape. |
| `points` | list, at least 2, in date order | Each `{ date, site, value, uncertainty_k1 }`; `site` must be one of `sites`. |
| `note` | text, *optional* | |

Views derive the number of scenes and sites, the period, the mean, the spread (sample standard deviation) and how many scenes are within their own k = 2 uncertainty of zero.

## Example reports

`node tools/build_cqas_examples.mjs` writes one example report per curated product; `--check` fails if any file would change (`npm test` runs it). Values are seeded from the product ID, so they differ between products but are the same on every run. Each product has a profile in the script, chosen to be plausible:

- **Requirements** come from the product's current CEOS-ARD specification ([ceos-org/ceos-ard](https://github.com/ceos-org/ceos-ard), extracted to `tools/data/ceos_ard_pfs_requirements.json` with its commit). Levels a specification does not have are `Not required`. At most two Threshold findings are Not met, nearly always for missing evidence.
- **Sites** suit the sensor: RadCalNet sites for current optical sensors, CEOS desert (PICS) sites for missions that predate RadCalNet, in situ temperature sites for thermal products and corner reflector arrays for radar.
- **Channels** are the sensor's own (for hyperspectral sensors, a few wavelengths near the multispectral bands). Radar uses the co-polarised channel, the one a trihedral reflector returns.
- **Pixel sizes** come from the catalogue. Where it has no single value, the profile names the variant used (marked "not in catalogue").
- **Radiometric tests** are left out, with a reason, for mosaics, polarimetric products and InSAR displacement.
- `landsat-c2-sr` keeps the findings and values of the original C-QAS report mock-up.

## Adding or replacing a report

1. Write `data/cqas/<product-id>.json` in this format. For a real C-QAS report, remove the product's profile from the generator, or the next run will overwrite the file.
2. Run `npm test`; validation lists every problem in the file.
3. Rebuild and republish.
