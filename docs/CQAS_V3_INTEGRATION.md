# CQAS v3 consumer proposal

Prepared against prototype commit 31ae6fd and producer Phase 5 branch at 830d5e9.
This is an additive consumer branch for review, not contract adoption or deployment.

Copy the producer's draft publication directory unchanged to `data/cqas-v3/` before
building. The loader follows `index.json` report entries, validates against the
vendored producer JSON Schema, verifies cross-references, summaries, maturity and
fixed simple-view wording, and checks catalogue bindings and relative paths.
Invalid entries are skipped with warnings; discovery remains available.

Each product page receives only its own list of versioned reports. The simple view
shows the producer statement, acquisition and processing label; details retain
source result IDs, measurements, units, uncertainty and finding reasons. No missing
geometric block is filled with numbers. A valid v3 publication takes precedence
over the product's v2 example in detail and compact summaries. Matching, ordering
and the formal CEOS-ARD assessment are unaffected.

The existing v2 parser and examples are unchanged. A separate view is necessary:
converting native result lists to a single v2 geometric block would lose evidence.
Series and advisory alert sidecars are now displayed on product pages and /monitoring.
Copy producer series publications into data/cqas-v3 unchanged, and copy the
separate cqas alerts output into data/cqas-alerts unchanged. Each directory keeps
its own index.json. Global service facts appear only in the monitoring view;
product panels match quality alerts to collection/site/check/measurement selectors.
A same-named series from another collection cannot claim product membership.

Each series segment gets a separate table, with null-valued gaps shown as dashes
and their original reasons. No lines cross gaps or changes. Boundary markers,
source records and source result IDs remain inspectable. Explicit sample minima
are presentation settings, not scientific sufficiency. Alert views separate measured
change from service availability, with timestamps and immutable evidence URIs.
Absent inputs or empty service lists never imply a healthy service.

In addition to schemas, the consumer checks observation/source projections,
segmentation, gap semantics, sample counts, summaries and alert calculations. It
retains the producer as the authority for cryptographic identity/evidence checks.
The consumer does not replace the producer's complete semantic validation, recompute
registration/content identity hashes, verify evidence-store objects, or establish
scientific validity. Treat bundled publications as reviewed repository inputs.

The fixture in tests/fixtures/cqas-v3/report.json is generated by the actual producer
build_report model from a synthetic unit-test registration and results. The binding
to sentinel2-level2a tests catalogue integration only; it is not an assessed scene
and is never bundled as live product data. Tests check unchanged ingestion, rejection,
path and catalogue gates and rendered source/missing-evidence text.

Validation: npm run check (0 errors/warnings); npm test (173 passed); npm run build;
npm run build:sites and npm run test:hosting passed. The standalone ESM validator
also loaded and validated the fixture directly in Node. Runtime validation uses
generated static code, not AJV compilation/eval in the Worker. The pretest hook
checks that the generated validator matches the vendored schema and generator.
Browser end-to-end checks run in repository CI; local socket restrictions prevent
starting the app here. Human reading and phase-end independent review remain open.

Sidecar extension verification is recorded in the producer Phase 5 evidence log.
The test fixtures series.json and alerts.json were generated by the producer models,
not hand-populated display values. They remain outside bundled product data.
